04 — How I work

Fast like vibe coding. Reviewed like it's payroll.

Everything above was built with an AI coding agent as my daily pair. That's how one engineer covers this much ground. The speed comes from AI; the reason it doesn't fall apart comes from a few habits.

AI drafts it

  • Scaffolding & CRUD controllers, requests, resources
  • Migrations & seeders from a schema I've designed
  • Exploring an unknown codebase or an undocumented database
  • Refactors across many files renames, extractions, upgrades
  • Clickable prototypes to agree on a flow first

I decide it

  • The data model and where tenant boundaries sit
  • Who can see and approve what roles, scopes, policies
  • Anything touching salaries calculations, locks, rounding
  • Whether the data can be trusted validated against reality
  • What reaches production every diff read before merge
Three habits that keep it from turning into a mess
/a

A design doc for every feature

Why it exists, its limits, and the decisions behind it. Each moves IDEATION → IN_DEV → PRODUCTION. The AI reads it before touching code, so feature #40 still respects what was decided in feature #3.

/b

Every change goes through a visible diff

No silent scripted rewrites, no history rewrites without me. If I can't review it line by line, it doesn't land.

/c

A monthly report in plain language

What shipped, what it fixed, and who it helped, written for management rather than engineers. Being able to explain the work is part of the work.
